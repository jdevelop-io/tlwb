# tlwb collaboration server: design

Date: 2026-08-26
Status: approved
Parent specification: `2026-08-08-tlwb-canvas-engine-realtime-design.md`
(section 6, "Collaboration server")
Sibling specification: `2026-08-26-tlwb-store-yjs-design.md` (the client
side of the wire protocol this server speaks)

## 1. Scope and goal

This specification covers `apps/collab-server` in full: the Node process
that turns an anonymous, local-first board into a hosted one. It creates
hosted boards and their share keys, relays Yjs updates and awareness
between the collaborators of a board, enforces read-only links, rejects
malformed elements before they reach anyone, persists every board in
Postgres, and stores the image blobs of hosted boards.

After this work, `apps/client` can call one HTTP endpoint when the user
presses Share, hand the resulting key to `connectBoard` from
`@tlwb/store-yjs`, and collaborate in real time with anyone holding the
link. The same Docker image serves the SaaS and the future self-hosted
Enterprise edition.

Implementation is planned in three slices: board creation, keys, and
persistence over HTTP first; then the WebSocket room with sync,
awareness, read-only enforcement, and validation; then assets, the
Docker image, and the Compose file.

## 2. Decisions and rationale

- A board becomes hosted through an unauthenticated `POST /boards`. No
  account is needed to share, per the product specification; abuse is
  bounded by rate limiting per IP. Implicit creation on the first
  WebSocket connection was rejected because the keys would then have to
  be generated by the client, and creation restricted to accounts
  contradicts the product.
- Image blobs of hosted boards live in Postgres (`bytea`), not in
  S3-compatible storage. One service to deploy, no MinIO, no S3 SDK, no
  credentials. Known ceiling: images of a few megabytes each, a few
  hundred per board; the storage sits behind one module so a move to S3
  is a local change. Amendment to the parent specification.
- Incoming elements are validated on the server, after applying the
  update to a staging copy of the document. A Yjs update is binary and
  cannot be inspected before it is applied, and Yjs cannot un-apply an
  update; the staging document is how "reject" is expressed. This closes
  the risk both parent specifications left open (a malformed element
  reaching every collaborator's engine).
- The room loop is written by hand on `y-protocols`. Read-only rejection,
  staging validation, and Postgres persistence have no clean hook in
  `y-websocket/bin/utils`, and Hocuspocus brings its own authentication
  protocol, incompatible with the `y-websocket` client already in place.
  The loop is about 150 lines.
- Drizzle ORM with `drizzle-kit` migrations over the `postgres` driver.
  Typed queries and versioned SQL migrations without writing the
  migration tooling ourselves. Tests run against a real Postgres, in
  Docker Compose locally and as a service container in CI, so there is
  no fake database to maintain.
- The server imports `yjs` directly. The "only `store-yjs` imports Yjs"
  rule of the parent specification protects the engine and the client;
  a server whose job is to relay Yjs updates has no reason to hide the
  library. The server reuses `createYjsBoardStore` from `@tlwb/store-yjs`
  to read elements out of a document rather than duplicating the
  document layout.
- `@tlwb/engine` gains `validateElement(value: unknown): value is
  BoardElement`, a `zod` schema over the element union, next to the
  existing `sanitizePeers`. The engine owns the element model, so it owns
  what a well-formed element is; the server and, later, the MCP server
  call it.

## 3. Package and architecture

`apps/collab-server` (`@tlwb/collab-server`), same tooling as the
packages: strict TypeScript, Vitest, Biome. The workspace already
includes `apps/*`.

Dependencies: `hono`, `@hono/node-server`, `ws`, `yjs`, `y-protocols`,
`drizzle-orm`, `postgres`, `@tlwb/engine`, `@tlwb/store-yjs`.
Development dependencies: `drizzle-kit`, `vitest`, `@types/ws`.

```
apps/collab-server/
  src/
    main.ts          reads the configuration, starts the server, handles SIGTERM
    server.ts        composition root: database, rooms, HTTP, WebSocket
    config.ts        environment variables, validated at boot
    keys.ts          key generation, hashing, constant-time comparison
    http.ts          Hono application: boards, assets, health
    ws.ts            WebSocket upgrade, token check, connection to room
    protocol.ts      y-sync and awareness message encoding on y-protocols
    room.ts          one board in memory: doc, connections, staging, writes
    rooms.ts         room registry: load on first connection, idle eviction
    rate-limit.ts    token bucket per connection
    db/
      schema.ts      Drizzle schema
      client.ts      connection and migration runner
      boards.ts      board and update queries, compaction
      assets.ts      blob queries
    migrations/      generated by drizzle-kit, committed
  test/
    keys.test.ts
    config.test.ts
    protocol.test.ts
    rate-limit.test.ts
    room.test.ts         staging validation over an in-memory Y.Doc
    boards.test.ts       HTTP creation and persistence (database)
    assets.test.ts       HTTP put and get (database)
    compaction.test.ts   snapshot plus residual updates (database)
    e2e.test.ts          real WebSocket with connectBoard as the client
  Dockerfile
  drizzle.config.ts
  package.json
```

Two surfaces on one port:

- HTTP through Hono: `POST /boards`, `PUT` and `GET
  /boards/:boardId/assets/:hash`, `GET /health`.
- WebSocket through `ws` on `/ws/:boardId?token=...`, the exact URL
  `connectBoard` builds today (`url` is `wss://host/ws`, the room name
  is the board identifier, `token` is the query parameter).

Each module has one responsibility and is testable alone; `server.ts`
wires them and nothing else.

## 4. Board creation and access control

### Creation

`POST /boards` with body `{ "boardId": string }`. The client supplies the
identifier it already uses locally (the IndexedDB database name is
derived from it), so a board keeps its identity when it becomes hosted.
The identifier must match `^[A-Za-z0-9_-]{8,64}$`.

- `201 { boardId, editKey, viewKey }` on success.
- `409` when the board exists. No key is returned, so guessing an
  identifier never yields access.
- `400` on a malformed identifier or body.
- `429` from the per-IP rate limit (default 10 creations per minute per
  IP).

The client keeps `editKey` alongside its local board and builds share
links from either key. The server never shows a key again.

### Keys

A key is 32 random bytes from `crypto.randomBytes`, encoded base64url.
The `boards` row stores the SHA-256 hash of each key; the clear key
exists only in the creation response. Verification hashes the presented
token and compares it to both columns with `crypto.timingSafeEqual`.
The result is a role, `edit` or `view`, or a rejection.

### WebSocket access

On upgrade, the server resolves the token before accepting the
connection:

- unknown board: close `4404`;
- token matching neither key: close `4401`;
- otherwise the connection joins the room with its role.

A `view` connection receives the full sync and awareness stream and may
publish its own awareness (cursor, name, selection). Any y-sync message
carrying an update from a `view` connection closes it with `4403`. The
connection is closed rather than the message silently dropped: the
engine's read-only mode never sends an update, so one arriving means a
modified client.

### Asset access

`PUT` requires the edit key, `GET` accepts either key, both through
`Authorization: Bearer <key>`. Missing or wrong key: `401`.

### What is not here

No `owner_id` column and no session check. The accounts specification
adds owner access by migration and by a second way to resolve a role on
upgrade.

## 5. Rooms, protocol, validation

### Room lifecycle

A room is created on the first connection to a board: the server loads
the snapshot and the residual updates from Postgres in `seq` order into
a fresh `Y.Doc`, then runs the standard y-sync handshake (`SyncStep1`,
`SyncStep2`) and sends the current awareness states. When the last
connection closes, an idle timer starts (default 60 seconds); when it
fires, the room compacts if needed and leaves memory. A connection
arriving during the timer cancels it.

### Update handling on an `edit` connection

1. Decode the message. A message larger than the limit (default 1 MB)
   closes the connection with `4409`.
2. Apply the update to the room's staging document. The staging document
   is a second `Y.Doc` kept in step with the room document: every
   accepted update is applied to both, so staging never needs a full
   copy. An observer on the staging `elements` map records the
   identifiers touched by the transaction.
3. Validate: each touched identifier is read through
   `createYjsBoardStore(staging).getElement(id)` and passed to
   `validateElement`; a deleted identifier is skipped. The `meta` map is
   checked as `{ name?: string, createdAt?: number }`. The encoded state
   of the staging document must stay under the document limit (default
   5 MB).
4. Accepted: apply the update to the room document, `INSERT` it into
   `board_updates`, then relay it to every other connection. Durability
   comes before relay so a crash never shows a peer an update the
   database does not have.
5. Rejected: the staging document is rebuilt from the room document
   (`encodeStateAsUpdate` into a fresh `Y.Doc`), the connection is
   closed with `4422`, and nothing is relayed or persisted. A message is
   accepted or rejected as a whole; there is no partial recovery of a
   mixed update.

### Awareness

Awareness messages are relayed unchanged to the other connections
through `y-protocols/awareness` and never persisted. A connection's
awareness state is removed from the room and announced to the peers
when it closes. One awareness state is limited in size (default 16 KB);
beyond that the connection closes with `4409`. Content is not validated:
every client already runs `sanitizePeers`.

### Rate limiting

A token bucket per connection (default 200 messages per 10 seconds)
regardless of message type. An empty bucket closes the connection with
`4429`. The `y-websocket` client reconnects with backoff, which is
enough of a signal; no ban list.

## 6. Persistence and assets

### Schema

- `boards`: `id text primary key`, `edit_key_hash bytea not null`,
  `view_key_hash bytea not null`, `snapshot bytea null`,
  `snapshot_seq bigint not null default 0`, `created_at timestamptz`,
  `updated_at timestamptz`.
- `board_updates`: `board_id text references boards(id)`,
  `seq bigserial`, `update bytea not null`, `created_at timestamptz`;
  primary key `(board_id, seq)`.
- `assets`: `board_id text references boards(id)`, `hash text`,
  `mime text not null`, `bytes bytea not null`, `created_at timestamptz`;
  primary key `(board_id, hash)`.

### Writes and compaction

Every accepted update is one immediate `INSERT`. No batching in v1; add
it when write throughput becomes measurable.

When a room holds more residual updates than the threshold (default
500), or when it is evicted, it compacts in one transaction: `UPDATE
boards SET snapshot = <encodeStateAsUpdate(doc)>, snapshot_seq = <last
seq>`, then `DELETE FROM board_updates WHERE board_id = $1 AND seq <=
snapshot_seq`. Loading reads `snapshot`, then the updates with `seq >
snapshot_seq`.

No automatic expiry of boards, updates, or assets, per the product
specification.

### Assets

`PUT /boards/:boardId/assets/:hash` takes the raw bytes as the body and
keeps `Content-Type` as the stored `mime`. Rules:

- only `image/*` types, otherwise `415`;
- body larger than the limit (default 10 MB): `413`;
- the SHA-256 of the received bytes must equal `:hash`, otherwise `400`;
- an existing `(board_id, hash)` answers `200` without rewriting;
  a new one answers `201`.

`GET /boards/:boardId/assets/:hash` returns the bytes with the stored
`Content-Type` and `Cache-Control: public, max-age=31536000, immutable`,
since the content is addressed by hash. Unknown hash: `404`.

No garbage collection of orphaned blobs; post-v1, like the client side.

### Migrations

`drizzle-kit generate` produces versioned SQL files under
`src/migrations/`, committed with the schema change that caused them.
The server applies pending migrations at boot through
`drizzle-orm/postgres-js/migrator`, so the Docker image is the whole
deployment and there is no separate migration step.

## 7. Configuration, deployment, error handling

### Configuration

Environment variables, validated at boot; a missing or malformed
required value exits with code 1 and the variable's name.

| Variable                | Default   | Meaning                                    |
| ----------------------- | --------- | ------------------------------------------ |
| `DATABASE_URL`          | required  | Postgres connection string                 |
| `PORT`                  | `3000`    | HTTP and WebSocket port                    |
| `CORS_ORIGIN`           | required  | Allowed origin for the HTTP API            |
| `MAX_MESSAGE_BYTES`     | `1048576` | WebSocket message limit                    |
| `MAX_DOC_BYTES`         | `5242880` | Encoded document state limit               |
| `MAX_ASSET_BYTES`       | `10485760` | Asset upload limit                        |
| `MAX_AWARENESS_BYTES`   | `16384`   | One awareness state limit                  |
| `ROOM_IDLE_MS`          | `60000`   | Idle time before a room leaves memory      |
| `COMPACT_AFTER_UPDATES` | `500`     | Residual updates before compaction         |
| `RATE_LIMIT_PER_10S`    | `200`     | Messages per connection per 10 seconds     |
| `CREATE_LIMIT_PER_MIN`  | `10`      | Board creations per IP per minute          |

### Deployment

`apps/collab-server/Dockerfile` is multi-stage: build TypeScript to
`dist/`, then `pnpm deploy --prod` into a `node:22-alpine` image that
carries only the production dependencies. A `docker-compose.yml` at the
repository root defines `postgres` (`postgres:17`) and `collab-server`;
the same file serves local development and the local test run.

On `SIGTERM` the server stops accepting connections, closes every
WebSocket with `1001`, compacts the open rooms, closes the pool, and
exits. TLS is terminated by the reverse proxy in front of the container.

### Error handling

HTTP errors answer JSON `{ "error": string }` with `400`, `401`, `403`,
`404`, `409`, `413`, `415`, or `429`.

WebSocket close codes:

| Code   | Meaning                                  |
| ------ | ---------------------------------------- |
| `1001` | Server shutting down                     |
| `1011` | Database write failed                    |
| `4401` | Token matches no key                     |
| `4403` | Update received on a read-only link      |
| `4404` | Unknown board                            |
| `4409` | Message or awareness state too large     |
| `4422` | Update produced a malformed element      |
| `4429` | Rate limit exceeded                      |

A Postgres error while inserting an update leaves the update unrelayed
and closes the connection with `1011`; the client resynchronizes on
reconnect, and the room document is rebuilt from the database on the
next load so memory and storage never diverge for long. A Postgres error
at boot (unreachable database, failed migration) exits with code 1.

Logs are JSON lines on stdout through `console`, one per connection
open, close with its code, room load, compaction, and error. No logging
library.

## 8. Testing

Vitest in a Node environment. Unit tests need no database; integration
and end-to-end tests read `DATABASE_URL` and run against the Compose
Postgres locally and a `postgres:17` service container in CI. Classical
TDD.

- Keys: two generated keys differ; the hash of a key verifies against
  its column and against nothing else; verification returns the role.
- Configuration: defaults apply; a missing `DATABASE_URL` fails with its
  name; a non-numeric limit fails.
- Protocol: a `SyncStep1` from a fresh client yields a `SyncStep2` that
  brings it to the room state; an awareness update round-trips.
- Rate limit: the bucket allows the burst, refuses the next message,
  allows again after refill.
- Room, in memory with two `Y.Doc` clients and no network: a valid
  update reaches the other client; an update that sets `x` to a string
  is rejected, the other client never sees it, and the next valid update
  from a third client still applies; an update pushing the document over
  the size limit is rejected.
- Boards over HTTP: `201` with two distinct keys; `409` on the same
  identifier; `400` on a bad identifier; the created board loads empty.
- Assets over HTTP: `PUT` then `GET` returns identical bytes and type;
  wrong hash `400`; non-image `415`; second `PUT` of the same hash
  `200`; `GET` with the view key succeeds, `PUT` with the view key
  `401`.
- Compaction: after more updates than the threshold, `board_updates`
  holds only the tail and a fresh load equals the in-memory document.
- End to end, real server on an ephemeral port, `connectBoard` from
  `@tlwb/store-yjs` as the client: two edit clients converge; a view
  client receives updates and is closed with `4403` when it sends one;
  a client sending a malformed element is closed with `4422` and the
  other client never sees the element; after the idle eviction of the
  room, a new connection loads the persisted state.

CI: the `verify` job gains a `postgres:17` service and a `DATABASE_URL`
environment variable; `pnpm test` covers the server like the packages.

## 9. Success criteria

- A board created through `POST /boards` and opened by two browsers with
  the edit link converges on every edit, and a third browser with the
  view link sees the edits and cannot make any.
- A malformed element never reaches another collaborator and never
  reaches the database.
- Stopping and restarting the server loses nothing: every accepted
  update is in Postgres before it is relayed.
- `docker compose up` brings a working server from a clean checkout.
- The engine's `validateElement` accepts every element `createElement`
  produces and rejects a missing or mistyped property.

## 10. Out of scope

Accounts and board ownership, the MCP server and its tokens,
S3-compatible asset storage, garbage collection of orphaned assets,
metrics and tracing beyond the JSON logs, TLS, horizontal scaling of
rooms across processes (one process per deployment in v1), and
validation of awareness content beyond its size.
